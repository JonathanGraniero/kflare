# Contributing to kflare

Thanks for helping. kflare is an alpha, so bug reports from real use are as valuable as code: if something behaves
differently from what [ARCHITECTURE.md](ARCHITECTURE.md) or the [deploy guide](docs/deploy.md) says, please open an
issue with the resource's YAML (without secrets), its `status`, and the kflare and Kubernetes versions.

Questions about installing or using kflare, and ideas, go to
[Discussions](https://github.com/JonathanGraniero/kflare/discussions). Security issues go through
[SECURITY.md](SECURITY.md), not public issues.

Everyone taking part follows the [Code of Conduct](CODE_OF_CONDUCT.md). [GOVERNANCE.md](GOVERNANCE.md) says how
decisions are made and how contributors become reviewers and maintainers, who are listed in
[MAINTAINERS.md](MAINTAINERS.md). If you run kflare, adding yourself to [ADOPTERS.md](ADOPTERS.md) helps too.

## What you need

- Go 1.26 or newer
- Docker, for kind (kind itself is pinned and downloaded by `make kind`)
- kubectl
- Helm, for `make test-e2e` and the Prometheus that `local/setup.sh` installs
- For anything that talks to Cloudflare: a Cloudflare account and an API token. A free account with R2 enabled and a
  zone on the Free plan are enough for every live test kflare has

The Makefile downloads its other tools (controller-gen, kustomize, setup-envtest, golangci-lint, kind) into `bin/`, at
pinned versions.

## Build and test

```sh
make build   # runs codegen, manifests, generate, fmt, fix and vet, then builds bin/manager
make test    # the same generators, then the unit and envtest suites (Kubernetes 1.34.1)
make lint    # golangci-lint
make vulncheck  # govulncheck: known vulnerabilities in the modules and the Go standard library the code calls
make crd-compat # breaking changes to the CRDs since the last release (see Changing a CRD; needs the tags)
```

CI runs `make test`, `make lint`, `make helm-lint`, `make vulncheck`, `make crd-compat` and a Docker build, scans the
image with Grype
(failing on a fixable vulnerability of high or critical severity), runs the envtest suites again on the newest
Kubernetes (`make test ENVTEST_K8S_VERSION=1.37.0`), and fails if `git diff` shows anything afterwards: commit what
the generators write, and run `go fix ./...` (part of `make test`) before you push. [SECURITY.md](SECURITY.md) lists
the other checks.

The unit tests need no Cloudflare account: each controller talks to Cloudflare through a narrow interface, and the
tests use fakes that follow what the live API was seen to do.

Fuzz tests cover the code that reads input kflare does not control: `FuzzReview` in `pkg/metricsauth` (whatever a
client of the metrics port sends) and `FuzzV7ErrorClassification` in `pkg/cloudflare` (whatever Cloudflare's API
answers). `make test` runs their seed inputs and those kept in the package's `testdata/fuzz`. To fuzz one for longer
(neither needs envtest):

```sh
go test ./pkg/cloudflare/ -run '^$' -fuzz '^FuzzV7ErrorClassification$' -fuzztime 5m
```

The fuzzer writes an input that fails to `testdata/fuzz/<target>/`: fix the code, and commit the file with the fix so
that `make test` keeps checking it.

The health checks the deploy guide gives Argo CD and Flux are tested the way those tools run them
(`test/gitopshealth`): Argo CD's Lua with the libraries it opens, and Flux's CEL in its environment. Their cases are
in `config/argocd/health_test.yaml`, in the format of Argo CD's built-in checks, and `config/flux/health_test.yaml`,
with inputs the API server accepts for their kinds. The shared specs check both on the conditions the controllers
write, and the live specs on each status they wait for, against Cloudflare. A new `Ready` reason goes into
`readyReasons`, and, if a person must act on it, into both checks' lists and deploy.md's copies of them; the tests
fail on a reason the controllers set that `readyReasons` lacks, and on a deploy.md that does not hold the checks as
they are.

## Generated code

Most kinds are generated by kflare-gen (`generator/`) from Cloudflare's Go SDK (cloudflare-go v7) and a committed
subset of its OpenAPI spec: KVNamespace, D1Database, R2Bucket, WorkerRoute, IPList, Tunnel, DNSRecord, WAFCustomRule,
RateLimitRule, ManagedRuleset, the five Rules kinds (TransformRule, RedirectRule, CacheRule, ConfigurationRule,
OriginRule) and ManagedTransform. kflare-gen writes the types, the reconciler and the registration of Zone,
TunnelConfiguration and WorkerScript too, whose fields and calls stay hand-written on cloudflare-go v0.119, in their
`<kind>_extras.go` and `<kind>_hooks.go`. What a generated kind does that its entry cannot say is in its hand-written
hooks, the same two files. `zz_generated.*` files say `DO NOT EDIT`: change the kind's entry in
`generator/generator.yaml`, or the generator, and run `make codegen`. `make sync-spec` refreshes the OpenAPI subset;
it is only needed when adding a kind or moving the SDK.

## Running kflare against a real account

Point kubectl at a kind cluster, install the CRDs and run the manager on your machine:

```sh
export CF_API_TOKEN=<token> CF_ACCOUNT_ID=<account ID>
./local/setup.sh      # kind cluster, CRDs, a token Secret, a CloudflareAccount named my-account, Argo CD, Prometheus
make run              # the manager, against the current kubeconfig
kubectl get cloudflareaccount my-account   # Ready=True once the token is valid
./local/teardown.sh   # when you are done
```

`setup.sh` also installs Argo CD (`local/argocd.sh`) with kflare's health check, to watch kflare resources sync in its
UI; the script prints how to open it. `INSTALL_ARGOCD=0 ./local/setup.sh` leaves it out, and `./local/argocd.sh` adds
it to a cluster you already have (`./local/argocd.sh uninstall` removes it again).

It also installs Prometheus and Grafana (`local/prometheus.sh`, from kube-prometheus-stack), with a kflare dashboard:
calls to Cloudflare by controller and status, resources by `Ready`, drift corrections, reconciles, and the manager's
CPU and memory. The script prints how to open them. Prometheus scrapes the manager either way the e2e suite runs it, so
the dashboard shows a run as it goes: `make test-e2e` turns the chart's ServiceMonitor on, and `hack/e2e-live.sh`
serves its manager's metrics on the kind network's gateway, where Prometheus looks for them. `INSTALL_PROMETHEUS=0
./local/setup.sh` leaves it out, `./local/prometheus.sh` adds it to a kind cluster you already have, and
`./local/prometheus.sh uninstall` removes it again.

kflare creates only what you apply, and takes over nothing that already exists unless a resource carries
`kflare.dev/adoption-policy` (see [Adoption and ownership](ARCHITECTURE.md#adoption-and-ownership)). Still, use a test
account or zone, not production.

To run your build the way users do, through the Helm chart, build the image, load it into kind and install the chart
from your checkout:

```sh
make docker-build IMG=kflare:dev
kind load docker-image kflare:dev --name kflare-dev
helm upgrade --install kflare ./helm/kflare -n kflare-system --create-namespace \
  --set image.repository=kflare,image.tag=dev
```

If pods cannot reach the API server (`dial tcp 10.96.0.1:443: i/o timeout`) and `kube-proxy` crash-loops with
`too many open files`, the host's inotify limits are too low for the number of kind clusters. Raise them:

```sh
sudo sysctl fs.inotify.max_user_instances=512 fs.inotify.max_user_watches=524288
```

## The Helm chart

`helm/kflare/templates/crds/` and `helm/kflare/files/manager-rules.yaml` are generated from `config/` by
`hack/sync-helm-chart.sh`. Run `make helm` after changing API types or RBAC markers; CI fails when they are out of
sync. `make helm-lint` lints and renders the chart. A new value goes in `values.yaml`, with a comment, and in
`values.schema.json`.

An installation scoped by `watchNamespaces` grants the RBAC markers' rules in two parts: those on what is cluster-wide
with its ClusterRole, and the others with a Role in each namespace it watches. `make helm` writes both from
`config/rbac/role.yaml` with `hack/chartrbac`, into `files/manager-cluster-rules.yaml` and
`files/manager-namespaced-rules.yaml`. A kflare kind goes by its CRD's scope; a marker on another resource makes the
command fail until `coreResources` there says where the chart grants it. The controller's envtest specs run managers
as users that hold only those rules, so a rule a scoped installation lacks fails them.

Artifact Hub lists the chart from its OCI repository. `helm/artifacthub-repo.yml` holds Artifact Hub's ID for that
repository, which makes kflare a verified publisher there; the `Artifact Hub` workflow pushes it to the chart's
`artifacthub.io` tag whenever it changes on `main`.

What the chart's Artifact Hub page shows comes from the annotations in `helm/kflare/Chart.yaml`. The license, category,
operator level and links are written by hand, above the marker line. `make helm` writes the rest with
`hack/chartannotations`: the controller image at the chart's version, which Artifact Hub scans for its security report;
each CRD, described by the first sentence of its type's comment after the "is the Schema for" line; one example per
kind, the first resource in the kind's sample in `config/samples/`; and the release's changes, from its CHANGELOG.md
section. So run `make helm` after changing a sample too. Artifact Hub drops a whole chart version over one annotation
it cannot read: `make helm` fails rather than write one, and the command's tests check the committed annotations, the
hand-written ones too, as Artifact Hub does.

The chart's `resources` and autoscaling targets come from `hack/sizing`, which runs the controller image in Docker
against an envtest API server, as a leader and a standby, and reports their CPU and memory while it adds Secrets and
kflare resources and then stops the leader. Run it again after a change that could move them, such as a new watch or
cache, and update the table in the deploy guide's
[Scaling and resources](docs/deploy.md#scaling-and-resources):

```sh
make docker-build sizing IMG=controller:latest SIZING_ARGS="-secrets 5000 -resources 5000 -samples /tmp/sizing.csv"
```

The deploy guide's [Reconciles at once](docs/deploy.md#reconciles-at-once) comes from `hack/resync`, which builds the
manager and times how long it takes to reconcile every resource once, as after a restart, with each
`--max-concurrent-reconciles` value given. It runs the manager on this machine against an envtest API server, with
`CloudflareAccount`s that each have a token of their own and `KVNamespace`s spread over them, and against a stand-in for
Cloudflare's API that answers each call after a fixed latency, reached through a proxy that inspects TLS, so the
manager's own client and rate limits run as in a cluster. Run it again after a change to the reconcilers' locks, the
rate limiter or the HTTP client:

```sh
make resync RESYNC_ARGS="-accounts 20 -resources 1000 -latency 200ms -workers 1,2,4,8,16"
```

## The live end-to-end suite

`make test-e2e` installs the manager with the Helm chart on the kind cluster in your current context, with the
chart's NetworkPolicy on, and checks that it starts and serves its metrics only to an authorized token. With
`CF_API_TOKEN` and `CF_ACCOUNT_ID` set, it also runs the live specs in `test/e2e/cloudflare_test.go` against your
account, and with `CF_E2E_ZONE` the zone-level ones against that zone. They create, change and delete one of each
resource, all named `kflare-e2e-<run>`, check Cloudflare's copy after each step, and clean up even when they fail.
`KFLARE_E2E_MANAGER=external` uses a manager you already run with `make run` instead of deploying one. To watch a run's
metrics, install Prometheus on the cluster first (`./local/prometheus.sh`, see
[Running kflare against a real account](#running-kflare-against-a-real-account)).

- The token needs the permissions in the [deploy guide](docs/deploy.md#1-create-a-cloudflare-api-token), plus
  Zone · Zone · Read on the zone. That set is verified to be enough on its own
- The zone is adopted with the retain policy and never deleted, but the specs write rules, records and routes in it.
  Use a zone you can spare
- A Free zone holds one rate limiting rule and a Free account one IP list, so two runs must never overlap
- A run deletes the ruleset entry points its rules made in the zone's phases, once they are empty. One the zone had
  before the run stays, as does one that holds a rule the run did not write

The same suite runs in GitHub Actions against the project's test account, on Kubernetes 1.37, in the `Live E2E`
workflow, and the upgrade specs against the account after it. It runs on every pull request from a branch of this
repository and on every push to `main` and the release branches, unless only Markdown files or `docs/` changed, next
to the `E2E` workflow: a smoke test of the deployment, with no Cloudflare credentials, and the upgrade from the last
release ([Changing a CRD](#changing-a-crd)). A pull request from a fork gets no secrets, so the live suite skips on
it: describe what you ran against your own account instead. It skips on Dependabot's pull requests too; a maintainer
runs it on one by hand (`gh workflow run live-e2e.yml --ref <branch>`). Runs never overlap, and only one waits: when
several are pushed at once, the older ones show as cancelled, and are re-run once the queue is empty.

## Changing a CRD

A change to a CRD can break an upgrade with every test passing: the API server goes on serving the stored resources,
but a manifest written for the last release may no longer apply, a stored resource can lose a field, and the same
manifests may fail on a new cluster. `make crd-compat`, which CI runs, compares `config/crd/bases` with the CRDs of
the newest release tag in your branch's history (`hack/crdcompat`). For each version that release served, it reports:

- a CRD, a version or a field removed or renamed, a version no longer served, and a new kind or scope
- a field's new type, a field newly required without a default, and a default added, changed or removed
- a tighter enum, bound, length or count, a pattern, format or CEL rule added or changed, and null or unknown fields
  no longer accepted
- a list or map whose type or keys change, which changes how a server-side apply merges it

While the API is an alpha, such a change can ship as [GOVERNANCE.md](GOVERNANCE.md) describes: list it in
CHANGELOG.md's Unreleased section, under a `### Breaking changes` heading that names each kind the check reports and
says how to upgrade. A version that is not an alpha cannot break: serve the change in a new version. For a tighter
rule, the notes should say what validation ratcheting leaves of a stored resource that fails it (checked on
Kubernetes 1.34): it can still be reapplied, write its status and be deleted, but its manifest no longer creates a
resource, and under a new CEL rule on an object, no other field of that object can change until the value is fixed.

The `E2E` workflow's `Upgrade from the last release` job (`make test-e2e-upgrade`) installs the last release's chart
on kind, applies a resource of each kind from `test/e2e/testdata/upgrade.yaml` as that release has it, and upgrades
the chart to your branch's. Every resource must then still apply as a GitOps sync would, also as a new resource on a
new cluster, and be reconciled again by the new manager, keeping what the release stored. In the `Live E2E` workflow the
resources reach Cloudflare first, and the new manager must find each one in sync and write nothing to Cloudflare.
Your branch's copy of the file is applied after the upgrade, so a resource that differs from the release's is the
migration your release notes describe: change one only along with its "Breaking changes" entry, and add one for a
new kind.

## Changing a controller

Every controller follows the loop [ARCHITECTURE.md](ARCHITECTURE.md#the-reconcile-loop) describes (spec → Cloudflare's
copy → difference → write only on drift), and the same conventions: a single `Ready` condition, set through the helpers
in `internal/controller/status.go`, with a successful reconcile ending in `readyWithDriftCheck`, which schedules the
next drift check; a paused resource left alone from the start of the reconcile (`reconciler.Paused`, reported with
`updatePaused`); `*Ref` fields instead of copied IDs; fields that identify the Cloudflare object
immutable through CEL; the adoption and deletion policies of `internal/controller/adoption.go` and
`reconciler.RetainOnDelete`; and the `kflare.dev/` prefix on every finalizer, label and annotation kflare owns.

A change to how a controller behaves comes with:
- unit or envtest specs for the new behavior, and its failure cases
- for a new controller or a new Cloudflare call: a live e2e spec, and the API behavior you checked live written down
  (what Cloudflare accepts, refuses and stores)
- a mutation check with `hack/mutate.sh` (it applies hand-written mutations to the code and expects the tests to fail
  for each), with every mutation caught
- the docs it changes: ARCHITECTURE.md for drift detection, adoption, error handling or deletion, the deploy guide for
  permissions and troubleshooting reasons, and the samples. Keep Markdown lines at 120 characters or fewer

## Branches and pull requests

- Branch from `main`: `feat/<name>` for features, `fix/<name>` for fixes, `docs/<name>` for documentation
- One change per pull request, against `main`, or against a release branch for a fix to an older minor release
  ([Patch releases from a release branch](#patch-releases-from-a-release-branch)). Don't base a pull request on another
  open one; wait for it to merge
- Merge `main` into your branch if it falls behind, rather than rebasing a branch others may have pulled
- Describe what changed and how you checked it: the tests, and for live behavior, what you ran against Cloudflare.
  The pull request template ([.github/pull_request_template.md](.github/pull_request_template.md)) lists the checks
- `main` and the release branches are protected: every change lands through a pull request whose checks (CI, the E2E
  smoke and upgrade tests, and the dependency review) pass on a branch up to date with the one it targets. A code
  owner ([.github/CODEOWNERS](.github/CODEOWNERS)) reviews and merges it

## Releasing

Maintainers release through a pull request that bumps `version` and `appVersion` in `helm/kflare/Chart.yaml`, adds the
release's section to [CHANGELOG.md](CHANGELOG.md) and runs `make helm`. The version follows
[Versioning and support](docs/versioning.md#release-versions): a minor release when Unreleased lists a breaking
change, a patch release otherwise. Unreleased's "Breaking changes" stay under that heading in the release's section,
where the CRD check finds them until the tag exists. Merging it releases that version:

1. The `Tag release` workflow waits for every job of CI and E2E on the merge commit, then tags it `vX.Y.Z` and starts
   the `Release` workflow on the tag. It releases only a merge that changes the version, to one newer than every tag,
   and stops before tagging if `appVersion` differs or CHANGELOG.md has no section for it
2. `Release` publishes the image (`linux/amd64` and `linux/arm64`, with an SBOM and provenance for each) and the chart
   to `ghcr.io`, signs both with cosign, keyless, and drafts the GitHub release with the SBOMs and the section as its
   notes (`hack/releasenotes`)
3. It checks the signatures as [Verifying a release](docs/deploy.md#verifying-a-release) does, without a login, then
   publishes the release, as latest unless a newer version is tagged, and starts `Release scan`

The notes are the section with its relative links made absolute, to the files at the tag, and each wrapped line joined
to the one it continues, since a release page shows every line break. Artifact Hub's changelog shows the bullets as
plain text, but for those under "Upgrading ..." and "Known limitations": write each change as one bullet (a list
nested in it joins its text), whose links Artifact Hub lists below it.

If a job of CI or E2E fails on the merge commit, nothing is tagged: rerun the failed jobs, then rerun `Tag release`. A
`vX.Y.Z` tag pushed by hand starts `Release` too, as does running it on a tag from the Actions tab. `Release` refuses a
tag that does not match `Chart.yaml`, a release that is published already, and a tag on a commit that is in the history
of neither `main` nor its minor release's branch, or on `main` but older than the newest version; rerun after a failed
step, it goes on with its draft.

CI tests the oldest and the newest Kubernetes minor kflare supports
([Kubernetes versions](docs/versioning.md#kubernetes-versions)). Supporting a new one changes CI's newest envtest
version (`ci.yml`), the kind images in `e2e.yml` and `live-e2e.yml`, and `HELM_KUBE_VERSIONS`. Dropping the oldest, in
a minor release only, changes `kubeVersion` in `Chart.yaml`, `ENVTEST_K8S_VERSION`, the smoke tests' matrix in
`e2e.yml`, `local/kind-config.yaml`, and the docs that name the version, which `git grep` finds. The jobs' names hold
their Kubernetes versions, so `main`'s required checks change with them.

### Patch releases from a release branch

A patch release that `main` cannot make comes from its minor release's `release-0.Y` branch: a security fix for the
minor release before the latest ([Supported releases](docs/versioning.md#supported-releases)), or a fix for the latest
once `main` holds a breaking change for the next one. The `protect release branches` ruleset protects the branch as
`protect main` protects `main`, and `require reviews` covers it too: changes come through pull requests, which merge
once CI's, E2E's and the dependency review's checks pass on a branch up to date with it.

1. **Cut the branch**, once for the minor release, from its newest patch's tag:

   ```sh
   git fetch --tags origin
   git push origin 'v0.4.3^{commit}:refs/heads/release-0.4'
   ```

   A branch runs the workflows its own files hold, so its checks take their names from the tag's, Kubernetes versions
   included. v0.4.2 and older run CI on `main` only, so `release-0.4` is cut from v0.4.3 or newer, which `main`
   releases before v0.5.0. `protect release branches` must require the branch's check names, which
   `gh api repos/JonathanGraniero/kflare/rules/branches/release-0.4` lists: change its checks to the new branch's, or,
   while an older release branch whose checks are named otherwise still gets fixes, give the new one a ruleset of its
   own
2. **Cherry-pick the fix** onto a branch from `release-0.4` (`git cherry-pick -x <commit>`), and open the pull request
   against `release-0.4`. Fix `main` first, unless only the older minor release needs the fix: CodeQL analyzes pull
   requests to `main` only. CI checks it as it checks `main`, comparing the CRDs with the minor release's newest patch
   and testing the upgrade from it: a patch release's notes list no breaking change, so the CRD check fails on any. A
   vulnerability in the Go standard library or in the image's base files needs no change, since the release builds the
   image with the newest Go 1.26 patch and base files. One in a Go module needs its fixed version on the branch
   (`go get <module>@<version>`, then `go mod tidy`): Dependabot opens pull requests for `main` only
3. **Prepare the release** as for `main`, in a pull request against `release-0.4`: the next patch version in
   `Chart.yaml`, its section in CHANGELOG.md above the branch's last release's, and `make helm`. The `Live E2E`
   workflow runs the live suite on it
4. **Tag its merge commit** by hand, once every job of CI and E2E has passed on it: `Tag release` releases only merges
   to `main`.

   ```sh
   git fetch origin release-0.4
   git tag -a v0.4.4 -m "kflare v0.4.4" <merge commit>
   git push origin v0.4.4
   ```

   `Release` publishes it as it does a release from `main`, with `release-0.4` as its target and as latest only if no
   newer version is tagged, then starts `Release scan`, which scans its image every week for as long as its minor
   release gets fixes
5. **Record it on `main`**, in a pull request: the release's section in main's CHANGELOG.md, below the newer minor
   release's sections. For a security fix, the GitHub security advisory names the fixed release of each supported
   minor release

The branch stays once its minor release gets no more fixes. The release scan's `release-image-previous-minor`
category then keeps the release's last report until the next minor release's turn: dismiss what it still shows as
won't fix.
