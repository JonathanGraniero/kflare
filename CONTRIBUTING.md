# Contributing to kflare

Thanks for helping. kflare is an alpha, so bug reports from real use are as valuable as code: if something behaves
differently from what [ARCHITECTURE.md](ARCHITECTURE.md) or the [deploy guide](docs/deploy.md) says, please open an
issue with the resource's YAML (without secrets), its `status`, and the kflare and Kubernetes versions.

Questions about installing or using kflare, and ideas, go to
[Discussions](https://github.com/JonathanGraniero/kflare/discussions). Security issues go through
[SECURITY.md](SECURITY.md), not public issues.

Everyone taking part follows the [Code of Conduct](CODE_OF_CONDUCT.md). [GOVERNANCE.md](GOVERNANCE.md) says how
decisions are made and how contributors become reviewers and maintainers, who are listed in
[MAINTAINERS.md](MAINTAINERS.md).

## What you need

- Go 1.26 or newer
- Docker, for kind (kind itself is pinned and downloaded by `make kind`)
- kubectl
- For anything that talks to Cloudflare: a Cloudflare account and an API token. A free account with R2 enabled and a
  zone on the Free plan are enough for every live test kflare has

The Makefile downloads its other tools (controller-gen, kustomize, setup-envtest, golangci-lint, kind) into `bin/`, at
pinned versions.

## Build and test

```sh
make build   # runs codegen, manifests, generate, fmt, fix and vet, then builds bin/manager
make test    # the same generators, then the unit and envtest suites (Kubernetes 1.34.1)
make lint    # golangci-lint
make vulncheck  # govulncheck: known vulnerabilities in the modules and the Go standard library the code calls
```

CI runs `make test`, `make lint`, `make helm-lint`, `make vulncheck` and a Docker build, scans the image with Grype
(failing on a fixable vulnerability of high or critical severity), runs the envtest suites again on the newest
Kubernetes (`make test ENVTEST_K8S_VERSION=1.37.0`), and fails if `git diff` shows anything afterwards: commit what
the generators write, and run `go fix ./...` (part of `make test`) before you push. [SECURITY.md](SECURITY.md) lists
the other checks.

The unit tests need no Cloudflare account: each controller talks to Cloudflare through a narrow interface, and the
tests use fakes that follow what the live API was seen to do.

Fuzz tests cover the code that reads input kflare does not control: `FuzzReview` in `pkg/metricsauth` (whatever a
client of the metrics port sends) and `FuzzV7ErrorClassification` in `pkg/cloudflare` (whatever Cloudflare's API
answers). `make test` runs their seed inputs and those kept in the package's `testdata/fuzz`. To fuzz one for longer
(neither needs envtest):

```sh
go test ./pkg/cloudflare/ -run '^$' -fuzz '^FuzzV7ErrorClassification$' -fuzztime 5m
```

The fuzzer writes an input that fails to `testdata/fuzz/<target>/`: fix the code, and commit the file with the fix so
that `make test` keeps checking it.

The health checks the deploy guide gives Argo CD and Flux are tested the way those tools run them
(`test/gitopshealth`): Argo CD's Lua with the libraries it opens, and Flux's CEL in its environment. Their cases are
in `config/argocd/health_test.yaml`, in the format of Argo CD's built-in checks, and `config/flux/health_test.yaml`,
with inputs the API server accepts for their kinds. The shared specs check both on the conditions the controllers
write. A new `Ready` reason goes into `readyReasons`, and, if a person must act on it, into both checks' lists and
deploy.md's copies of them; the tests fail on a reason the controllers set that `readyReasons` lacks, and on a
deploy.md that does not hold the checks as they are.

## Generated code

Most kinds are generated by kflare-gen (`generator/`) from Cloudflare's Go SDK (cloudflare-go v7) and a committed
subset of its OpenAPI spec: KVNamespace, D1Database, R2Bucket, WorkerRoute, IPList, Tunnel, DNSRecord, WAFCustomRule,
RateLimitRule, ManagedRuleset, the five Rules kinds (TransformRule, RedirectRule, CacheRule, ConfigurationRule,
OriginRule) and ManagedTransform. kflare-gen writes the types, the reconciler and the registration of Zone,
TunnelConfiguration and WorkerScript too, whose fields and calls stay hand-written on cloudflare-go v0.119, in their
`<kind>_extras.go` and `<kind>_hooks.go`. What a generated kind does that its entry cannot say is in its hand-written
hooks, the same two files. `zz_generated.*` files say `DO NOT EDIT`: change the kind's entry in
`generator/generator.yaml`, or the generator, and run `make codegen`. `make sync-spec` refreshes the OpenAPI subset;
it is only needed when adding a kind or moving the SDK.

## Running kflare against a real account

Point kubectl at a kind cluster, install the CRDs and run the manager on your machine:

```sh
export CF_API_TOKEN=<token> CF_ACCOUNT_ID=<account ID>
./local/setup.sh      # kind cluster, CRDs, a token Secret, a CloudflareAccount named my-account and Argo CD
make run              # the manager, against the current kubeconfig
kubectl get cloudflareaccount my-account   # Ready=True once the token is valid
./local/teardown.sh   # when you are done
```

`setup.sh` also installs Argo CD (`local/argocd.sh`) with kflare's health check, to watch kflare resources sync in its
UI; the script prints how to open it. `INSTALL_ARGOCD=0 ./local/setup.sh` leaves it out, and `./local/argocd.sh` adds
it to a cluster you already have (`./local/argocd.sh uninstall` removes it again).

kflare creates only what you apply, and takes over nothing that already exists unless a resource carries
`kflare.dev/adoption-policy` (see [Adoption and ownership](ARCHITECTURE.md#adoption-and-ownership)). Still, use a test
account or zone, not production.

To run your build the way users do, through the Helm chart, build the image, load it into kind and install the chart
from your checkout:

```sh
make docker-build IMG=kflare:dev
kind load docker-image kflare:dev --name kflare-dev
helm upgrade --install kflare ./helm/kflare -n kflare-system --create-namespace \
  --set image.repository=kflare,image.tag=dev
```

If pods cannot reach the API server (`dial tcp 10.96.0.1:443: i/o timeout`) and `kube-proxy` crash-loops with
`too many open files`, the host's inotify limits are too low for the number of kind clusters. Raise them:

```sh
sudo sysctl fs.inotify.max_user_instances=512 fs.inotify.max_user_watches=524288
```

## The Helm chart

`helm/kflare/templates/crds/` and `helm/kflare/files/manager-rules.yaml` are generated from `config/` by
`hack/sync-helm-chart.sh`. Run `make helm` after changing API types or RBAC markers; CI fails when they are out of
sync. `make helm-lint` lints and renders the chart. A new value goes in `values.yaml`, with a comment, and in
`values.schema.json`.

Artifact Hub lists the chart from its OCI repository. `helm/artifacthub-repo.yml` holds Artifact Hub's ID for that
repository, which makes kflare a verified publisher there; the `Artifact Hub` workflow pushes it to the chart's
`artifacthub.io` tag whenever it changes on `main`.

What the chart's Artifact Hub page shows comes from the annotations in `helm/kflare/Chart.yaml`. The license, category,
operator level and links are written by hand, above the marker line. `make helm` writes the rest with
`hack/chartannotations`: the controller image at the chart's version, which Artifact Hub scans for its security report;
each CRD, described by the first sentence of its type's comment after the "is the Schema for" line; one example per
kind, the first resource in the kind's sample in `config/samples/`; and the release's changes, from its CHANGELOG.md
section. So run `make helm` after changing a sample too. Artifact Hub drops a whole chart version over one annotation
it cannot read: `make helm` fails rather than write one, and the command's tests check the committed annotations, the
hand-written ones too, as Artifact Hub does.

The chart's `resources` and autoscaling targets come from `hack/sizing`, which runs the controller image in Docker
against an envtest API server, as a leader and a standby, and reports their CPU and memory while it adds Secrets and
kflare resources and then stops the leader. Run it again after a change that could move them, such as a new watch or
cache, and update the table in the deploy guide's
[Scaling and resources](docs/deploy.md#scaling-and-resources):

```sh
make docker-build sizing IMG=controller:latest SIZING_ARGS="-secrets 5000 -resources 5000 -samples /tmp/sizing.csv"
```

## The live end-to-end suite

`make test-e2e` installs the manager with the Helm chart on the kind cluster in your current context, with the
chart's NetworkPolicy on, and checks that it starts and serves its metrics only to an authorized token. With
`CF_API_TOKEN` and `CF_ACCOUNT_ID` set, it also runs the live specs in `test/e2e/cloudflare_test.go` against your
account, and with `CF_E2E_ZONE` the zone-level ones against that zone. They create, change and delete one of each
resource, all named `kflare-e2e-<run>`, check Cloudflare's copy after each step, and clean up even when they fail.
`KFLARE_E2E_MANAGER=external` uses a manager you already run with `make run` instead of deploying one.

- The token needs the permissions in the [deploy guide](docs/deploy.md#1-create-a-cloudflare-api-token), plus
  Zone · Zone · Read on the zone. That set is verified to be enough on its own
- The zone is adopted with the retain policy and never deleted, but the specs write rules, records and routes in it.
  Use a zone you can spare
- A Free zone holds one rate limiting rule and a Free account one IP list, so two runs must never overlap
- Runs leave empty ruleset entry points in some of the zone's phases. They hold no rules and change nothing; delete
  them if you like

The same suite runs in GitHub Actions against the project's test account, on Kubernetes 1.37 (the `E2E` workflow).
Pull requests and pushes to `main` run only a smoke test of the deployment, with no Cloudflare credentials. A
maintainer runs the live suite on a pull request with a review comment starting with `/live-e2e`. A pull request from
a fork gets no secrets, so the live suite cannot run on it: describe what you ran against your own account instead.
Runs never overlap.

## Changing a controller

Every controller follows the loop [ARCHITECTURE.md](ARCHITECTURE.md#the-reconcile-loop) describes (spec → Cloudflare's
copy → difference → write only on drift), and the same conventions: a single `Ready` condition, set through the helpers
in `internal/controller/status.go`, with a successful reconcile ending in `readyWithDriftCheck`, which schedules the
next drift check; a paused resource left alone from the start of the reconcile (`reconciler.Paused`, reported with
`updatePaused`); `*Ref` fields instead of copied IDs; fields that identify the Cloudflare object
immutable through CEL; the adoption and deletion policies of `internal/controller/adoption.go` and
`reconciler.RetainOnDelete`; and the `kflare.dev/` prefix on every finalizer, label and annotation kflare owns.

A change to how a controller behaves comes with:
- unit or envtest specs for the new behavior, and its failure cases
- for a new controller or a new Cloudflare call: a live e2e spec, and the API behavior you checked live written down
  (what Cloudflare accepts, refuses and stores)
- a mutation check with `hack/mutate.sh` (it applies hand-written mutations to the code and expects the tests to fail
  for each), with every mutation caught
- the docs it changes: ARCHITECTURE.md for drift detection, adoption, error handling or deletion, the deploy guide for
  permissions and troubleshooting reasons, and the samples. Keep Markdown lines at 120 characters or fewer

## Branches and pull requests

- Branch from `main`: `feat/<name>` for features, `fix/<name>` for fixes, `docs/<name>` for documentation
- One change per pull request, against `main`. Don't base a pull request on another open one; wait for it to merge
- Merge `main` into your branch if it falls behind, rather than rebasing a branch others may have pulled
- Describe what changed and how you checked it: the tests, and for live behavior, what you ran against Cloudflare
- `main` is protected: every change lands through a pull request whose checks (CI, the E2E smoke tests and the
  dependency review) pass on a branch up to date with `main`. A code owner ([.github/CODEOWNERS](.github/CODEOWNERS))
  reviews and merges it

## Releasing

Maintainers release by bumping `version` and `appVersion` in `helm/kflare/Chart.yaml`, adding the release's section to
[CHANGELOG.md](CHANGELOG.md) and running `make helm`, through a pull request, then pushing a `vX.Y.Z` tag that matches
them. The GitHub release's notes are that section. Artifact Hub's changelog shows its bullets as plain text, but for
those under "Upgrading ..." and "Known limitations": write each change as one bullet (a list nested in it joins its
text), whose links Artifact Hub lists below it. The `Release` workflow refuses a tag that does not match, and otherwise
publishes the image (`linux/amd64` and `linux/arm64`, with an SBOM and provenance for each) and the chart to `ghcr.io`,
signs both with cosign, keyless, and drafts the GitHub release with the SBOMs. A maintainer then replaces the draft's
notes with the CHANGELOG.md section and publishes it.
